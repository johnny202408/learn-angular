# פרק 16. ביצועים: זיהוי שינויים, `OnPush`, `@defer`, ניתוח bundle

Compass מהיר על המחשב הנייד שלך. הוא כנראה לא מהיר על טלפון בן חמש שנים ב-4G. הפרק הזה סוגר את הפער הזה. אנחנו מודדים את Compass, מיישמים את ארבע הטכניקות שחשובות ביותר באפליקציית Angular, ומסיימים עם Compass קטן ומהיר יותר שמוכן לעולם האמיתי.

ארבע הטכניקות:

1. זיהוי שינויים `OnPush` (או, טוב יותר, זיהוי שינויים מונע-סיגנלים).
2. בלוקי `@defer` לחלקי UI שלא צריכים להיטען מיד.
3. `NgOptimizedImage` לתמונות שחוסמות זמן-להיות-אינטראקטיבי.
4. ניתוח bundle, כדי לראות מה המשתמשים שלך מורידים בפועל.

נגע גם ב-Angular ללא zone — כיוון ההתקדמות שמחבר כמה מאלה יחד.

## מדוד קודם

לעולם אל תבצע אופטימיזציה בלי למדוד. Angular נותנת לך שלוש תצוגות טובות לתוך הביצועים, והדפדפן נותן לך רביעית.

**Angular DevTools** היא הרחבת דפדפן שמראה את עץ הקומפוננטות שלך עם מדדי זיהוי שינויים. בכל פעם ש-Angular בודקת קישורי קומפוננטה, היא רושמת כמה זמן זה לקח. קומפוננטות איטיות צבועות באדום. התקן אותה מחנות ההרחבות של Chrome או Edge ופתח אותה דרך פאנל ה-DevTools הרגיל של הדפדפן.

**טאב הביצועים ב-DevTools של הדפדפן** מקליט את כל ה-thread הראשי. פתח אותו, לחץ הקלט, לחץ מסביב ב-Compass, עצור. תראה את תרשים הלהבה של כל פונקציה שרצה. חפש משימות ארוכות (>50ms) ופונקציות גבוה בתרשים הלהבה.

**Lighthouse** (מובנה ב-Chrome DevTools) מריץ ביקורת סינתטית שכוללת Largest Contentful Paint, Total Blocking Time, ו-Cumulative Layout Shift — המדדים ש-Google משתמשת בהם כדי לדרג ביצועים נתפסים על ידי משתמשים.

**`ng build --configuration production`** בונה bundle ממוטב ומדפיס את גדלי הקבצים הסופיים. זו הדרך המהירה ביותר לראות אם שינוי הגדיל או הקטין את ההורדה.

הרץ את כל הארבעה לפני שאתה נוגע בשום דבר. אם Compass כבר מהיר מספיק עבור מכשירי היעד שלך, סגור את הפרק הזה.

## זיהוי שינויים: הסיפור הקלאסי

זיהוי השינויים ברירת המחדל של Angular הוא *טיול עץ*. אחרי כל אירוע (לחיצה, תגובת HTTP, setTimeout, פתרון Promise), Angular הולכת בכל עץ הקומפוננטות ובודקת כל קישור. אם ערך של קישור השתנה מאז הבדיקה האחרונה, היא מעדכנת את ה-DOM.

Zone.js היא הספרייה שמיירטת כל API אסינכרוני כדי להפעיל את הטיול הזה. בלעדיה, ל-Angular אין מושג מתי הקוד שלך שינה מצב.

הטיול מהיר באפליקציות קטנות. הוא הופך איטי כשלעץ יש אלפי קישורים או כשקישור יחיד קורא למתודה שעושה עבודה אמיתית.

### `ChangeDetectionStrategy.OnPush`

אתה יכול לגרום לקומפוננטה לצאת מהטיול-עץ ברירת המחדל. מצב `OnPush` אומר ל-Angular: "בדוק את הקומפוננטה הזאת רק כשאחת מהתייחסויות ה-input שלה משתנה, או כשאירוע נורה עליה, או כש-Observable שהיא מנויה אליו דרך פייפ `async` פולט, או כשאחד מהסיגנלים שהיא קוראת משתנה".

```ts
import { Component, ChangeDetectionStrategy } from '@angular/core';

@Component({
  selector: 'app-task-row',
  changeDetection: ChangeDetectionStrategy.OnPush,
  // ...
})
```

`OnPush` מפחית את כמות הבדיקה בצורה דרמטית. באפליקציה כבדת-סיגנלים כמו שלנו, תופעות הלוואי שלה בקושי גלויות — סיגנלים כבר יודעים אילו קומפוננטות קוראות אותן, ורק אלה נבדקות.

תרגול מיטבי: **הגדר `OnPush` בכל קומפוננטה**. בקוד מונע-סיגנלים, אתה מקבל דיוק בחינם. בקוד שמערבב סיגנלים ודפוסים ישנים יותר, `OnPush` מכריח אותך להיות מפורש לגבי מצב, שזה דבר טוב.

### ללא zone: כיוון ההתקדמות

Angular מודרנית יכולה לרוץ בלי Zone.js לגמרי. זיהוי שינויים מופעל רק משינויי סיגנל וממספר מקורות מנוהלי-Angular. כל `setTimeout` או `Promise.resolve()` כבר לא מתזמנים בדיקה מחדש.

הפעלתו היא שורה אחת ב-`app.config.ts`:

```ts
import { provideExperimentalZonelessChangeDetection } from '@angular/core';

providers: [
  provideExperimentalZonelessChangeDetection(),
  // הסר את provideZoneChangeDetection() אם הוא שם.
],
```

אחר כך הסר את ה-polyfill `zone.js` מ-`angular.json` (במערך `polyfills`).

באפליקציה סיגנל-קודם — ש-Compass היא — ללא zone עובד. החלקים שהיו נשברים תחת ללא zone הם:

- קוד שמסתמך על `setTimeout` לגרום לרנדור מחדש. שכתב לעדכון סיגנל.
- שרשראות `Promise.then` שמעדכנות מצב בלי לעבור דרך סיגנלים או פייפ `async`. אותו תיקון.
- ספריות צד שלישי שמשגרות אירועי DOM מחוץ למודעות של Angular. עטוף את מקור האירוע עם סיגנל או Observable ש-Angular יכול לעקוב אחריו.

ללא zone עדיין מסומן כניסיוני בזמן כתיבת הספר, אבל כל החלטת עיצוב בספר הזה הייתה מוכנה-ללא-zone. מעבר בעתיד צריך להיות commit אחד.

## בלוקי `@defer`

חלקי UI מסוימים לא נחוצים בצביעה הראשונה. עמוד "סטטיסטיקות" של Compass יש לו ספריית תרשימים שהוא יכול לטעון עצל. עמוד פירוט משימה יש לו גלריית תמונות שחשובה רק כשהמשתמש גולל אליה. סעיף "unsubscribe" של עמוד הגדרות מבוקר לעתים רחוקות.

בלוקי `@defer` דוחים את הטעינה והרנדור של חתיכה של תבנית עד שתנאי מתקיים. התחביר:

```html
@defer (on viewport) {
  <app-heavy-chart [data]="stats()" />
} @placeholder {
  <div class="chart-placeholder">Loading chart…</div>
} @loading (after 100ms; minimum 300ms) {
  <div class="spinner"></div>
} @error {
  <p>Could not load the chart.</p>
}
```

החלקים:

- **`@defer (on viewport)`** — התחל טעינה כשה-placeholder נכנס לתצוגה.
- **`@placeholder`** — מה לרנדר לפני שהטריגר נורה. חייב להיות מרקאפ פשוט; אין קומפוננטות כבדות כאן (או שה-placeholder עצמו הופך כבד).
- **`@loading`** — מה לרנדר בזמן שהחתיכה הדחויה מורדת, אם זה לוקח מספיק זמן כדי לשווה להראות.
- **`@error`** — מה לרנדר אם הטעינה נכשלת.

טריגרים אחרים חוץ מ-`on viewport`:

- `on idle` — כשהדפדפן לא פעיל אחרי טעינת דף.
- `on interaction` — כשהמשתמש מעביר עכבר או מתמקד על אלמנט שצוין.
- `on hover` — מקרה מיוחד של interaction.
- `on timer(30s)` — אחרי עיכוב קבוע.
- `on immediate` — ברגע שהאפליקציה לא פעילה (לעתים רחוקות שימושי; אם זה מיידי, למה לדחות?).
- `when someSignal()` — טריגר תוכניתי.

בלוקים דחויים הם chunks נפרדים בפלט הבנייה. הם מורדים ברקע, בחתיכות לפי טריגר. `@defer` הוא הידית הבודדת הגדולה ביותר שיש לרוב אפליקציות Angular להפחתת גודל bundle ראשוני בלי לטעון עצל מסלולים שלמים.

עבור Compass, נדחה את התרשים של עמוד הסטטיסטיקות עד שה-container נכנס לתצוגה. זה חוסך את ספריית התרשים (כמה מאות KB) מה-bundle הראשוני.

## `NgOptimizedImage`

תמונות הן לעתים קרובות הנכס הגדול ביותר בעמוד. הדירקטיבה `NgOptimizedImage` של Angular מטפלת ברמזי גודל, טעינה עצלה מתחת לקפל, טעינה עדיפה של תמונת LCP, וכמה טריקים אחרים ש-Lighthouse-audit דורש.

יבא והשתמש:

```ts
import { NgOptimizedImage } from '@angular/common';

@Component({
  imports: [NgOptimizedImage],
  // ...
})
```

```html
<img ngSrc="/assets/hero.jpg" width="800" height="400" priority alt="Compass" />
<img ngSrc="/assets/footer.jpg" width="1200" height="300" alt="footer" />
```

הערות:

- `ngSrc` (לא `src`) מפעיל את הדירקטיבה.
- `width` ו-`height` נדרשים. הם מונעים תזוזת layout.
- `priority` מסמן את התמונה הזאת כמועמדת LCP. כלול אותו על תמונה אחת לכל היותר לכל מסך.
- תמונות מחוץ למסך בלי `priority` נטענות עצל כברירת מחדל.

עבור Compass אין לנו הרבה תמונות (זו אפליקציה כבדת-טקסט), אבל אם תוסיף avatar של משתמש או icon של הרגל, השתמש ב-`NgOptimizedImage`.

## ניתוח Bundle

`ng build` מדפיס גדלי קבצים. זו התחלה. למבט אמיתי על מה שיש בתוך ה-bundle שלך, השתמש ב-`source-map-explorer`:

```bash
npm install --save-dev source-map-explorer
ng build --configuration production --source-map
npx source-map-explorer dist/compass/browser/main-*.js
```

הוא פותח treemap אינטראקטיבי של ה-bundle שלך: מודולים צבועים לפי גודל, מקובצים לפי מקור. בדרך כלל תמצא:

- **Angular עצמה**: 150–250 KB gzip. לא הרבה מה אפשר לעשות בקשר לזה.
- **הקוד שלך**: בדרך כלל זעיר לאפליקציה קטנה; הקובץ שבזבזת עליו שבוע הוא 10 KB.
- **ספריות צד שלישי**: לעתים קרובות ההפתעה. ספריית תרשימים, ספריית תאריכים, או סט icons יכולים להאפיל על הכל.

שתי הידיות כשספריות צד שלישי דומיננטיות:

- **Tree-shaking**. ייבא רק את מה שאתה משתמש. `import { format } from 'date-fns'` מארז רק את `format`; `import * as dateFns from 'date-fns'` מארז את כל הדבר.
- **טעינה עצלה או דחויה**. העבר את הספרייה מאחורי `@defer` או מסלול עצל. היא לא צריכה להיות ב-bundle הראשוני.

Compass משתמש במעט מאוד ספריות צד שלישי. אם תרחיב אותו — עם ספריית תרשים לעמוד הסטטיסטיקות, נניח — יישם את הידיות האלה מוקדם.

## `trackBy` ב-`@for`, שוב

פגשת את `track` בפרק 6. זה חשוב גם לביצועים.

```html
@for (task of tasks(); track task.id) {
  <app-task-row [task]="task" />
}
```

בלי `track`, Angular הייתה יוצרת מחדש כל צומת DOM כשההתייחסות של המערך משתנה. עם `track task.id`, Angular משתמשת מחדש בצמתים לפי זהות — מעבירה אותם אם עמדות השתנו, מוסיפה חדשות ל-ids חדשים, מסירה צמתים ל-ids נעדרים. צמתים שנעשה בהם שימוש חוזר משמרים focus, אנימציות, וכל מצב אימפרטיבי.

לרשימות ארוכות — מאות פריטים — `track` לפי id יציב הוא ההבדל בין "מיידי" ל"עצל".

לרשימות באמת ענקיות (אלפים), פנה ל-*virtual scrolling*: ה-CDK של Angular Material כולל `cdk-virtual-scroll-viewport` שמרנדר רק את הפריטים הנראים. Compass לעולם לא יצטרך אותו, אבל הוא קיים.

## `computed` ו-memoization

`computed` שומר במטמון. זו אחת המעלות שלו.

```ts
readonly expensiveDerivation = computed(() => {
  // הגוף הזה רץ רק כשהתלויות שלו משתנות.
  return tasks().sort(complexComparator).slice(0, 20);
});
```

אם התבנית שלך קוראת ל-`expensiveDerivation()` בעשרה מקומות, הגוף רץ פעם אחת לכל שינוי ל-`tasks`, ועשר הקריאות מחזירות את התוצאה השמורה. חילוץ ביטויי תבנית יקרים ל-`computed` הוא אחד הרווחים האמינים ביותר בקוד מונע-סיגנלים.

האנטי-דפוס: מתודה יקרה שנקראת מהתבנית. `<span>{{ formatComplex(x) }}</span>` מריץ את `formatComplex` בכל זיהוי שינויים. חלץ: `readonly formatted = computed(() => formatComplex(x()))` וקרא `formatted()`.

## OnPush + סיגנלים ב-Compass

הפעל `OnPush` לרוחב Compass:

```ts
// כל קומפוננטה:
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  // ...
})
```

כי Compass קורא מצב דרך סיגנלים, זה לא משנה שום דבר נצפה — אבל זה מניח את היסודות ל-ללא zone. הפיגומים של Angular עצמה (דרך `ng generate component --change-detection=OnPush`) מגדיר את זה עבורך אם אתה מגדיר את זה כברירת מחדל של ה-CLI.

הוסף `@defer` לסעיף התרשים של עמוד הסטטיסטיקות. הוסף `NgOptimizedImage` לכל תמונה שתוסיף. הוסף `computed` לכל נגזרת יקרה. זה 95% מחוכמת הביצועים הספציפית ל-Angular.

## דברים שאינם ספציפיים ל-Angular שחשובים

ביצועי פריימוורק יכולים לעזור רק במידה מסוימת אם הסביבה שבורה. שתי רשימות בדיקה שאינן של Angular:

- **HTTP איטי.** שמור תגובות במטמון בשרת, השתמש ב-CDN, השתמש בדחיסת Brotli, השתמש ב-HTTP/2 או HTTP/3, השתמש ב-service workers אם offline חשוב. ה-SSR של פרק 18 עוזר לזמן-לצביעה-הראשונה; בחירות הפריסה של פרק 19 משפיעות על כל הנ"ל.
- **פונטים כבדים.** כל פונט מותאם אישית הוא בקשת רשת שחוסמת רנדור טקסט. סנן את הפונטים שלך. השתמש ב-`font-display: swap`. שקול פונטים של המערכת אם אתה יכול.

אם ביקורת ה-Lighthouse שלך רעה ואתה לא יכול למצוא את בעיית Angular, הסתכל מחוץ ל-Angular.

## מה בא הלאה

חלק חמישי מתחיל בבדיקות. פרק 17 מציג את `TestBed`, component harnesses, ו-Playwright עבור בדיקות מקצה לקצה. עד סוף חלק חמישי, ל-Compass יש חבילת בדיקות ותכנית פריסה, ופרק 20 שולח אותך לעולם Angular הרחב יותר.

### תרגילים

1. הפעל `OnPush` על כל קומפוננטה ב-Compass. הרץ את האפליקציה; וודא שהכל עדיין עובד. אז שבור משהו בכוונה (קרא ל-`this._tasks().push(...)` ב-`TaskStore` — שינוי במקום במקום עדכון). מה קורה תחת `OnPush`? מה התיקון? רשום את הכלל.

2. עטוף את (העדיין-לא-נבנתה) קומפוננטת `StatsChart` בבלוק `@defer` בעמוד הסטטיסטיקות. הפעל ב-viewport עם placeholder שקורא "Loading chart…". וודא בטאב הרשת שה-chunk של התרשים מוריד רק כשאתה גולל.

3. הרץ `source-map-explorer` נגד בניית ההפקה של Compass. מה שלושת הדברים הגדולים ביותר ב-bundle שלך? עבור כל אחד, החלט אם ניתן לטעון אותו עצל, לדחות, או tree-shake.
