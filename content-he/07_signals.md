# פרק 7. סיגנלים: מצב ריאקטיבי שמרגיש רגיל

הקוד של Compass שיש לך עכשיו עובד. לחץ על משימה, היא עוברת; הוסף משימה, היא מופיעה; נקה את ה-input, הכפתור מושבת מחדש. זה עובד כי Angular מריצה *זיהוי שינויים* — בדיקה של כל קישור בכל קומפוננטה נראית — אחרי כל אירוע DOM. באפליקציות קטנות זה בסדר. באפליקציות גדולות זה הופך לצוואר בקבוק, וזה מקשה על החשיבה על *למה* משהו רונדר מחדש.

סיגנלים הם התשובה של Angular לשתי הבעיות. סיגנל הוא פיסה של מצב ריאקטיבי שיודעת בדיוק מי מסתכל עליה. כשסיגנל משתנה, רק החלקים של המסך שקוראים את הסיגנל הזה מסומנים לרנדור מחדש — שום דבר אחר. ברגע שהקומפוננטות שלך קוראות סיגנלים במקום שדות רגילים, Angular יכולה לעדכן את המסך בדייקנות במקום בסחיפה. המודל המנטלי הוא *ערכים שדוחפים*.

הפרק הזה מציג סיגנלים, משכתב את הקוד של פרק 6 של Compass לשימוש בהם, ומכסה מתי לפנות ל-computed ול-effect. עד הסוף יהיה לך מודל מנטלי למצב ריאקטיבי שידריך כל פרק שנשאר.

## הבעיה שסיגנלים פותרים

דמיין מסך Compass עם מאה משימות ושלוש קומפוננטות בעמוד: רשימת המשימות, ציפ "נותרו" בכותרת, ופס התקדמות בתחתית. כל השלוש תלויות באותם נתונים.

במודל של לפני סיגנל, הזרימה היא: אתה לוחץ על משימה, הדגל `done` שלה מתהפך, ו-Angular בודקת מחדש כל קישור בעמוד — מאה `[class.done]`, את `{{ remaining }}` של הכותרת, את `[style.width]` של פס ההתקדמות, וכל השאר. Angular מהירה מספיק כדי שזה בדרך כלל לא נראה, אבל המנגנון הוא: *כשיש ספק, בדוק מחדש הכל*.

עם סיגנלים, הזרימה היא: אתה לוחץ על משימה; הסיגנל `done` של המשימה משתנה; Angular יודעת בדיוק אילו קישורי תבנית קוראים את הסיגנל הזה (`[class.done]` אחד, פריט אחד בחישוב `remaining`, פריט אחד בחישוב `progress`) ומעדכנת רק אותם. עשרים עדכונים במקום עשרת אלפים.

הזכייה בביצועים אמיתית אבל לא הסיבה לפנות לסיגנלים. הסיבה היא ש*הקוד שלך* הופך מדויק. ל"מאיפה הערך הזה מגיע?" יש תמיד תשובה — שרשרת של סיגנלים וחישובים שאתה יכול לעקוב אחריה. ל"למה זה רונדר מחדש?" יש תמיד תשובה — סיגנל שהוא קורא השתנה.

## יצירת סיגנל

הסיגנל הפשוט ביותר עוטף ערך יחיד:

```ts
import { signal } from '@angular/core';

const count = signal(0);
```

כדי *לקרוא* את הסיגנל, קרא לו כפונקציה:

```ts
console.log(count());   // 0
```

זה במכוון. סיגנלים הם פונקציות, וקריאה היא פעולה. כל קריאה מנוטרת — Angular רושמת מי קרא את הסיגנל כדי שיוכל להודיע לו מאוחר יותר.

כדי *לכתוב*, השתמש ב-`set` או ב-`update`:

```ts
count.set(10);
count.update(n => n + 1);
```

`set` מחליף את הערך; `update` מחשב את הערך הבא מהנוכחי. לרוב המצב, שניהם מתחלפים. `update` שימושי כשהערך החדש תלוי בישן — מונה, החלפה, הוספה למערך.

זה הכל. קרא עם `()`, כתוב עם `set` או `update`, ו-Angular עושה את השאר.

## קריאה בתבניות

אותו כלל חל בתבניות: כדי לקרוא סיגנל, קרא לו כפונקציה.

```html
<p>Count: {{ count() }}</p>
```

הסוגריים לא אופציונליים. `{{ count }}` מדפיס את אובייקט הפונקציה עצמה (משהו כמו `[object Function]`). הקומפיילר לא יתפוס את זה — זה נראה כמו TypeScript תקין — כך ששגיאה עם הסוגריים היא טעות נפוצה בהתחלה. אם האינטרפולציה שלך מדפיסה `function(){...}` בדפדפן, שכחת את ה-`()`.

## סיגנלים של מערכים ואובייקטים

סיגנל יכול להחזיק כל ערך, כולל מערכים ואובייקטים. אבל סיגנלים עוקבים אחר *התייחסויות*, לא אחר מצב עמוק. אם אתה משנה מערך במקום, לסיגנל אין מושג ששום דבר השתנה והוא לא יודיע לקוראים שלו.

```ts
const tasks = signal<Task[]>([]);

// לא נכון: משנה במקום, בלי הודעה
tasks().push(newTask);

// נכון: ייצר מערך חדש
tasks.update(current => [...current, newTask]);
```

זה אותו דפוס "ייצר אובייקט חדש" שפגשנו בפרק 3, עכשיו עם שם. עדכונים immutable הם איך שסיגנלים עובדים. זה נשמע לא נוח בפעם הראשונה; זה הופך לטבע שני במהירות, וזה גורם לשינויי מצב להיות נראים וניתנים לבדיקה.

## `computed`: ערכים נגזרים

סיגנל computed הוא סיגנל שערכו נגזר מסיגנלים אחרים. הוא מחשב מחדש כשהקלטים שלו משתנים, ושומר את התוצאה במטמון עד שהם משתנים.

```ts
import { computed } from '@angular/core';

const tasks = signal<Task[]>([]);
const remaining = computed(() => tasks().filter(t => !t.done).length);
const done = computed(() => tasks().length - remaining());
```

אתה קורא computed באותה דרך שאתה קורא כל סיגנל: `remaining()`. אתה אף פעם לא כותב ל-computed — הערך שלו הוא פונקציה של הקלטים שלו ואי אפשר להגדיר אותו ישירות.

שני דברים הופכים את `computed` לחזק:

- **מעקב תלויות אוטומטי.** הפריימוורק צופה באילו סיגנלים הפונקציה שלך קוראת. אם הסיגנלים האלה משתנים, ה-computed רץ מחדש. אם לא, הוא לא. אתה אף פעם לא רושם תלויות ידנית.
- **הערכה עצלה ומטמון.** ה-computed לא רץ עד שמשהו קורא אותו. ברגע שהוא רץ, התוצאה שלו במטמון; קריאות עוקבות מחזירות את המטמון. המטמון מבוטל כשכל תלות משתנה. אם ה-computed `progress` שלך תלוי ב-`tasks`, ו-`tasks` לא משתנה, `progress()` לא עולה כלום לקרוא לו חמישים פעם.

## `effect`: תופעות לוואי בקצה

חלק מהדברים צריכים לקרות *כשסיגנלים משתנים*, אבל לא מייצרים ערך. שמירה ל-`localStorage`, עדכון כותרת הדף, רישום ניתוחים, קריאה לספרייה שאינה Angular — אלה הן *אפקטים*.

```ts
import { effect } from '@angular/core';

class TaskList {
  tasks = signal<Task[]>([]);

  constructor() {
    effect(() => {
      const current = this.tasks();
      localStorage.setItem('compass:tasks', JSON.stringify(current));
    });
  }
}
```

הפונקציה של האפקט רצה פעם אחת מיד (כדי לבסס תלויות) ושוב בכל פעם שכל סיגנל שהיא קוראת משתנה. כאן היא שומרת את רשימת המשימות הנוכחית ל-`localStorage` בכל שינוי.

כללי הדרך לאפקטים:

- **רשום אפקטים בהקשר DI.** בקומפוננטה, זה אומר הקונסטרוקטור או אתחול שדה מחלקה. מחוץ להם, השתמש ב-`runInInjectionContext`.
- **אף פעם אל תכתוב לסיגנל מתוך אפקט.** לעשות זאת יוצר לולאה שבה האפקט מפעיל את עצמו. Angular תסרב להריץ את האפקט אם היא מזהה את הדפוס הזה.
- **פנה קודם ל-`computed`.** אם אתה מוצא את עצמך כותב אפקט שקורא סיגנלים ומחשב ערך, זה computed. אפקטים הם לפלטים לעולם החיצוני.

אפקטים הם הדבר הכי קרוב לרגל-פיתיון שיש לסיגנלים. בשימוש טוב, הם מחליפים hooks של מחזור חיים ו-subscriptions ל-observables. בשימוש רע, הם יוצרים פעולות רפאים מרחוק. פרק 14 חוזר אליהם כשנבנה שכבת מצב מבוססת סיגנלים.

## שכתוב Compass עם סיגנלים

זמן להמיר את `TaskList` מפרק 6. פתח את `src/app/task-list/task-list.ts` ושנה אותו ל:

```ts
import { Component, signal, computed } from '@angular/core';
import { Task } from '../task';

@Component({
  selector: 'app-task-list',
  imports: [],
  templateUrl: './task-list.html',
  styleUrl: './task-list.css',
})
export class TaskList {
  tasks = signal<Task[]>([
    /* ... שלושת המשימות ההתחלתיות מפרק 5 ... */
  ]);

  draft = signal('');

  remaining = computed(() =>
    this.tasks().filter(t => !t.done).length
  );

  toggle(taskId: string): void {
    this.tasks.update(current =>
      current.map(t =>
        t.id === taskId ? { ...t, done: !t.done } : t
      )
    );
  }

  add(): void {
    const title = this.draft().trim();
    if (title === '') return;
    this.tasks.update(current => [
      ...current,
      {
        id: crypto.randomUUID(),
        title,
        done: false,
        createdAt: new Date().toISOString(),
        dueDate: null,
        tags: [],
      },
    ]);
    this.draft.set('');
  }

  onInput(event: Event): void {
    this.draft.set((event.target as HTMLInputElement).value);
  }
}
```

ואת `task-list.html`:

```html
<h1>Tasks — {{ remaining() }} left</h1>

<form (submit)="add(); $event.preventDefault()">
  <input
    type="text"
    placeholder="What needs doing?"
    [value]="draft()"
    (input)="onInput($event)" />
  <button type="submit" [disabled]="draft().trim() === ''">Add</button>
</form>

<ul class="task-list">
  @for (task of tasks(); track task.id) {
    <li class="task" [class.done]="task.done" (click)="toggle(task.id)">
      <span class="title">{{ task.title }}</span>
      @if (task.dueDate) {
        <span class="due">due {{ task.dueDate | date: 'shortDate' }}</span>
      }
    </li>
  } @empty {
    <li class="empty">Nothing to do. Nice.</li>
  }
</ul>
```

שמור, רענן. Compass נראה ומתנהג אותו הדבר כמו קודם. כל שורת קוד חשובה, אבל, שונה:

- `tasks` ו-`draft` הם סיגנלים, נקראים עם `()`.
- `toggle` ו-`add` משתמשים ב-`update` כדי לייצר מערך חדש; שום דבר לא משתנה במקום.
- `remaining` מחושב פעם אחת, ומחושב מחדש רק כש-`tasks` משתנה.
- התבנית קוראת לסיגנלים: `remaining()`, `draft()`, `tasks()`.

מתחת למכסה, Angular עכשיו יודעת בדיוק אילו חלקים של התבנית תלויים באילו סיגנלים. אם נגרום לקומפוננטה הזאת להיות `changeDetection: ChangeDetectionStrategy.OnPush` — שפרק 16 מסביר ושנחיל גלובלית — Angular תסרב לבדוק שום דבר שלא היה יכול להשתנות. זה מודל הביצועים של אפליקציה מונעת סיגנלים.

## Signal inputs

*Inputs* של קומפוננטה — ערכים שמועברים מהורה — הוכרזו היסטורית עם הדקורטור `@Input()`:

```ts
export class TaskRow {
  @Input() task!: Task;
}
```

Angular מודרנית מציעה חלופה מבוססת סיגנלים: `input()` (ו-`input.required()`), שמייצרת סיגנל.

```ts
import { Component, input } from '@angular/core';

@Component({ /* ... */ })
export class TaskRow {
  task = input.required<Task>();

  // במתודות וב-computed, קרא אותו כמו כל סיגנל אחר:
  isOverdue = computed(() => {
    const t = this.task();
    return t.dueDate !== null && new Date(t.dueDate) < new Date();
  });
}
```

שתי צורות שימושיות:

- **`input<Type>()`** — אופציונלי; ברירת המחדל היא `undefined`, והסיגנל מחזיר `Type | undefined` אלא אם תספק ברירת מחדל: `input<number>(0)`.
- **`input.required<Type>()`** — נדרש; הקומפיילר אוכף שכל הורה יספק ערך.

Signal inputs הם ברירת המחדל המודרנית. הם מתחברים באופן טבעי עם `computed` (כמו למעלה) ועם `effect`. כשפרק 8 יעצב מחדש את Compass לעץ של קומפוננטות, נשתמש ב-`input()` לכל אורכו.

## Model inputs: two-way binding, כראוי

`ngModel` הוא דרך אחת לקבל two-way binding על inputs native; אחרת היא `[(value)]` על הקומפוננטות שלך, מופעל על ידי *model inputs*.

```ts
import { Component, model } from '@angular/core';

@Component({
  selector: 'app-quantity-picker',
  template: `
    <button (click)="value.set(value() - 1)">−</button>
    <span>{{ value() }}</span>
    <button (click)="value.set(value() + 1)">+</button>
  `,
})
export class QuantityPicker {
  value = model.required<number>();
}
```

הורה משתמש בו עם התחביר `[(name)]`:

```html
<app-quantity-picker [(value)]="count" />
```

`model` נותן לך סיגנל שניתן לכתיבה שמפיץ אוטומטית שינויים להורה דרך output מותאם. זו החלפה מודרנית לזוג "input + output" שקוד Angular ישן יותר השתמש בו. פרק 8 חוזר ל-model inputs לצד inputs רגילים.

## מתי להשתמש בסיגנלים — ומתי לא

כלל האצבע: **סיגנלים למצב שחי בתוך האפליקציה שלך**; **RxJS לזרמים מהעולם החיצוני**.

- **השתמש בסיגנלים ל:** מצב UI (פתוח/סגור, id שנבחר, טיוטת טופס), מצב נגזר (רשימה מסוננת, ספירות מחושבות), חישובים ריאקטיביים, ומצב חוצה שהיית שומר קודם בשירות (פרק 14 מכסה חנויות סיגנלים).
- **השתמש ב-RxJS ל:** תגובות HTTP (שהן באופן טבעי observables), זרמי אירועי DOM שצריכים debounce או `switchMap`, חיבורי WebSocket, זרמי נתונים ארוכי-טווח.
- **השתמש בשדות רגילים ל:** ערכים שאף פעם לא משתנים לאורך חיי הקומפוננטה, או שלא משפיעים על התבנית. אם כלום לא קורא את זה ריאקטיבית, זה לא צריך להיות סיגנל.

לפנות לסיגנלים בכל מקום היא טעות של מתחיל. לפנות ל-RxJS בכל מקום היא טעות של Angular בקריירה מוקדמת. שניהם עולים בפשטות. פרק 11 מכסה את ה-interop ביניהם (יש `toSignal` ו-`toObservable`, ושניהם שתי שורות קוד).

## זיהוי שינויים בעולם של סיגנלים

זיהוי שינויים ב-Angular היה פעם *מבוסס zone*: ספרייה שנקראת Zone.js תיקנה כל API אסינכרוני בדפדפן (טיימרים, Promises, XHR, מאזיני אירועים) כדי ש-Angular תוכל ללמוד מתי כל אחד מהם נורה ולבדוק מחדש את האפליקציה. זה עובד, אבל זה מברשת רחבה ועולה במידה של CPU בכל אירוע.

Angular מודרנית זזה לעבר אפליקציות *ללא zone*. באפליקציה ללא zone, Angular בודקת מחדש רק כשסיגנל משתנה. אין בדיקה מחדש סביבתית בכל setTimeout; אין Promise מוטלא. קישורים שקוראים סיגנלים מדויקים; שום דבר אחר לא רץ.

ברירת המחדל של `ng new` עדיין מפעילה Zone.js לתאימות לאחור, אבל הכיוון ברור. כל החלטת עיצוב בספר הזה — סיגנלים למצב, `input()` על פני `@Input()`, `model()` ל-two-way — היא במסלול ללא zone. אם אתה עוקב אחר הדפוסים של הספר הזה, הגירה ללא zone מאוחר יותר תהיה שינוי תצורה, לא שכתוב.

## מה בא הלאה

פרק 8 שובר את `TaskList` המונוליתי של Compass לעץ של קומפוננטות: רשימה, שורות בודדות, וטופס להוספת משימה. תפגוש הרכבה של קומפוננטות כראוי — `input()`, `output()`, והזרקת תוכן — ועד הסוף יהיה לך Compass שמובנה כמו אפליקציית Angular אמיתית, לא כמוכחת קונספט.

### תרגילים

1. הוסף סיגנל computed `overdueCount` שסופר משימות ש-`dueDate` שלהן בעבר ושהן לא `done`. הצג אותו מתחת לכותרת: "3 overdue." הצג את השורה רק כשיש לפחות משימה אחת שבאיחור.

2. הוסף `effect` שמתעד לקונסולה בכל פעם שרשימת המשימות משתנה, בפורמט `"tasks: 5 (2 done)"`. אחר כך לחץ מסביב וקרא את הקונסולה. מתי האפקט נורה? האם הוא נורה כשאתה מקליד ב-input? למה או למה לא?

3. הוסף כפתור "clear completed". הוא צריך להיות מושבת כשאין דבר שהושלם. חבר אותו לעדכון הסיגנל `tasks` על ידי סינון של משימות שבוצעו. השתמש ב-`update`, לא ב-`set`; אל תשנה את המערך.
