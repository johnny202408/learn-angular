# פרק 2. TypeScript מספיק ל-Angular

הפרק הזה הוא ידע עבודה של TypeScript, שנכתב לאנשים שלא השתמשו בה קודם ולא רוצים להפוך לחוקרי TypeScript במשרה מלאה. בסוף תוכל לקרוא כל ביטוי TypeScript שהספר משתמש בו, ולכתוב משלך בלי לנחש. לא תדע — ואל תשאף לדעת — כל מה ש-TypeScript יכולה לעשות. מערכת הטיפוסים שלה עמוקה מספיק כדי שיהיה לה מדף ספרים משלה; אנחנו לא מבקרים במדף הזה היום.

הדוגמאות בפרק הזה מונעות על ידי Compass. בכל פעם שנציג תכונה חדשה של TypeScript, נראה אותה עם צורה שתהיה לך אחר כך באפליקציה שלך: משימה, הרגל, משתמש, אירוע השלמה. כך, עד שנתחיל לכתוב קומפוננטות ב-Angular בפרק 5, הטיפוסים כבר ירגישו מוכרים.

## למה טיפוסים בכלל

אם כתבת סקריפט קטן בשפה כמו Python או JavaScript רגיל, כנראה כתבת משהו כזה:

```js
function totalMinutes(sessions) {
  let sum = 0;
  for (const s of sessions) sum += s.duration;
  return sum;
}
```

זה עובד. זה גם לא נותן לך שום עזרה. במקום אחר בתוכנית, קולגה מעביר לך מערך של *מחרוזות* בטעות, או אובייקט שמאיית את השדה `durationMinutes` במקום `duration`. הפונקציה עדיין רצה; היא מייצרת `NaN` או `"0[object Object]"` או משהו אחר סוריאליסטי, ועד שאתה שם לב, אתה צד אחר המקור של המוזרות בפלט.

TypeScript מוסיפה כמות קטנה של טקסים כדי למנוע את הציד הזה. אתה מוסיף הערה למה שפונקציה מצפה; הקומפיילר של TypeScript בודק כל מקום שהפונקציה נקראת בו; אם קורא מפר את החוזה, אתה מגלה מייד, לפני שהקוד רץ. בעורך, זה מתגלה כקו אדום גלי מתחת לשורה הבעייתית והודעה ספציפית על מה שגוי. בבנייה, זה עוצר את הבנייה.

אותה פונקציה ב-TypeScript:

```ts
interface Session {
  duration: number;
}

function totalMinutes(sessions: Session[]): number {
  let sum = 0;
  for (const s of sessions) sum += s.duration;
  return sum;
}
```

עכשיו הקומפיילר יודע: הפונקציה מקבלת מערך של דברים שיש להם שדה `duration` שהוא מספר, ומחזירה מספר. תעביר לה משהו אחר ו-TypeScript תתנגד. אין שום קסם בזה — הקומפיילר פשוט בודק ששמות וצורות מסכימים — אבל התמורה בקוד גדול יותר מקובץ אחד משמעותית. Angular בנויה להישען על התמורה הזאת.

## הרצת TypeScript, בפסקה אחת

TypeScript היא לא משהו שדפדפנים מריצים ישירות. כלי שנקרא הקומפיילר של TypeScript (`tsc`) קורא קבצי `.ts`, בודק את הטיפוסים, ומייצר קבצי JavaScript רגילים שדפדפן (או Node.js) יכול להריץ. בפרויקטי Angular, אתה כמעט אף פעם לא מפעיל את `tsc` בעצמך; ה-CLI של Angular מריץ אותו כחלק מ-`ng serve` ו-`ng build`. לפרק הזה, אם אתה רוצה לנסות TypeScript בבידוד, השתמש ב-**TypeScript Playground** באתר `typescriptlang.org/play` — הוא נותן לך להקליד TypeScript משמאל ולראות את ה-JavaScript המהודר מימין, בלי התקנה. מפרק 4 והלאה, ה-CLI לוקח פיקוד.

## הפרימיטיבים

הטיפוסים הבסיסיים של TypeScript הם `string`, `number`, `boolean`, `null` ו-`undefined`. יש אחרים, אבל אלה אלה שתקליד מאה פעמים ביום.

```ts
let title: string = "Buy milk";
let priority: number = 2;
let done: boolean = false;
let due: string | null = null; // עוד על "|" בעוד רגע
```

TypeScript חכמה בהסקת טיפוסים כשאתה מציב ערך בנקודת ההצהרה:

```ts
let title = "Buy milk";  // מוסק כ-string
```

אתה לא צריך לכתוב `: string` כשהערך כבר אומר ל-TypeScript מה המשתנה מחזיק. בפועל, אתה מוסיף הערות טיפוסים על *פרמטרים של פונקציות וטיפוסי החזרה*, על *צורות של אובייקטים*, ועל דברים שאתה עומד להקצות אליהם אחר כך; אתה משאיר את כל השאר להסקה. קוד שמוסיף הערות לכל `let` טריוויאלי הוא קוד מלא רעש.

> **הערה.** `null` ו-`undefined` שונים ב-TypeScript, כמו שהם ב-JavaScript. Angular נוטה להעדיף `null` עבור "אנחנו יודעים שאין כאן ערך" ולשמור את `undefined` עבור "הערך מעולם לא הוצב". שדה שהוא *אופציונלי* הוא כזה שאולי הוא `undefined`; שדה שהוא *nullable* הוא כזה שקיים אבל אולי הוא `null`. זו הבחנה עדינה שתהיה חשובה בפרק 12 כשנדבר על טפסים.

## מערכים וטאפלים

הטיפוס של מערך הוא `Type[]`, או במקביל `Array<Type>`:

```ts
const priorities: number[] = [1, 2, 3];
const tags: string[] = ["home", "work"];
```

מערכים ריקים צריכים הערה כי אין מה להסיק מהם:

```ts
const completed: string[] = [];   // בסדר
const uh = [];                    // מוסק כ-any[], שאתה לא רוצה
```

טאפלים הם מערכים באורך קבוע וטיפוסים לפי מיקום. תשתמש בהם לעתים רחוקות בקוד אפליקציה:

```ts
const point: [number, number] = [42, 7];
```

## טיפוסי אובייקט עם `interface`

הלחם והחמאה של TypeScript באפליקציית Angular הוא תיאור הצורה של אובייקטים. TypeScript מציעה שתי דרכים לעשות את זה — `interface` ו-`type` — ולצורות של אובייקטים הן כמעט חליפיות. השתמש ב-`interface` לצורות של אובייקטים; השתמש ב-`type` לאיחודים, לחיתוכים, ולדברים שהם לא סתם אובייקט.

הנה הטיפוס המרכזי של Compass, כפי שיופיע בפרק 5:

```ts
interface Task {
  id: string;
  title: string;
  done: boolean;
  createdAt: string;    // תאריך ISO 8601
  dueDate: string | null;
  tags: string[];
}
```

ערך שטוען שהוא `Task` חייב להכיל את כל שישה השדות האלה, עם הטיפוסים האלה. שדות נוספים הם שגיאה (ברוב ההקשרים). שדות חסרים הם שגיאה. טיפוסים שגויים הם שגיאה. הצורה הזאת הופכת לחוזה שכל חלק של האפליקציה יכול להסתמך עליו.

### מאפיינים אופציונליים, readonly, וחתימות אינדקס

תפגוש שלוש הערות שמשנות את התנהגות השדה.

```ts
interface Habit {
  id: string;
  name: string;
  color?: string;                // עשוי להיות undefined
  readonly createdAt: string;    // לא ניתן להקצות מחדש אחרי בנייה
  metadata: { [key: string]: string };  // מפה שרירותית string→string
}
```

`color?: string` אומר שהשדה אופציונלי; ערך שמקיים את `Habit` לא חייב לכלול אותו, ואם הוא שם הוא עשוי להיות `string` או `undefined`. `readonly` מונע הקצאה מחדש דרך הטיפוס הזה — מועיל לשדות בסגנון id שאסור לשנות במקום. הצורה האחרונה, `{ [key: string]: string }`, נקראת *חתימת אינדקס*; היא אומרת "כל מפתח מסוג string ממופה לערך מסוג string" ומועילה למילונים פתוחים.

## איחודי טיפוסים וטיפוסים ליטרליים

טיפוס *איחוד* הוא ערך שיכול להיות אחד מכמה טיפוסים. כבר ראית אחד: `string | null`. איחודים הם "או" מוגבל: הערך הזה הוא *או* מחרוזת *או* הערך `null`.

איחודים של מחרוזות ליטרליות הם אחד הדפוסים הכי שימושיים של TypeScript:

```ts
type Status = "todo" | "doing" | "done" | "archived";

interface Task {
  id: string;
  title: string;
  status: Status;
}
```

עכשיו `status` לא יכול להיות מחרוזת שרירותית; הוא חייב להיות בדיוק אחד מארבעת אלה. נסה לכתוב `task.status = "in-progress"` ו-TypeScript תסרב. כך אתה אוכף סט סגור של אפשרויות — enum של עני, וברוב המקרים הבחירה הטובה יותר.

> **שים לב.** ל-TypeScript יש מילת מפתח `enum`, והשנים הראשונות של Angular השתמשו בה בכבדות. הפרקטיקה המודרנית היא להעדיף איחודי מחרוזות ליטרליות. `enum` נהדק לאובייקטים JavaScript של זמן ריצה, שמגדילים את ה-bundle שלך; איחודי טיפוסים נהדקים לכלום (הם קיימים רק בזמן בדיקת הטיפוסים). פרק 5 משתמש באיחודים לכל אורכו.

## צמצום טיפוסים

אם למשתנה יש טיפוס איחוד, TypeScript תסיק *צמצום* שלו בתוך ענף של קוד שהיא יכולה לומר בו מה הערך באמת:

```ts
function greeting(name: string | null): string {
  if (name === null) {
    return "Hello, stranger.";
  }
  // כאן, TypeScript יודעת ש-name הוא string, לא string | null.
  return `Hello, ${name}.`;
}
```

שלושת דפוסי הצמצום הנפוצים ביותר:

- `typeof x === "string"` מצמצם את `x` ל-`string`.
- `x === null` או `x === undefined` מצמצמים דרך `if`ים.
- `"field" in x` מצמצם לתת-הקבוצה של איחוד שיש לה את השדה.
- `x instanceof Foo` מצמצם ל-`Foo`.

צמצום הוא אחת התכונות שגורמות ל-TypeScript להרגיש כאילו היא *עוזרת* במקום נלחמת. אם TypeScript אי פעם אומרת "אולי undefined" ואתה יודע שלא, התשובה כמעט תמיד היא לבדוק עם `if`, לא לעקוף את הבדיקה.

## פונקציות

טיפוסי פונקציה מוסיפים הערות לפרמטרים, ואופציונלית לטיפוסי החזרה:

```ts
function isOverdue(task: Task, now: Date): boolean {
  if (task.dueDate === null) return false;
  return new Date(task.dueDate) < now;
}
```

פונקציות חץ עובדות אותו הדבר:

```ts
const isOverdue = (task: Task, now: Date): boolean => {
  if (task.dueDate === null) return false;
  return new Date(task.dueDate) < now;
};
```

אם TypeScript יכולה להסיק את טיפוס ההחזרה מהגוף, אתה יכול להשמיט את ההערה — אבל זו פרקטיקה טובה להוסיף הערות לטיפוסי החזרה בפונקציות מיוצאות, כי זה מכריח אותך לחשוב על מה שפונקציה בעצם מבטיחה להחזיר.

פרמטרים של פונקציה יכולים להיות אופציונליים או שיהיו להם ברירות מחדל:

```ts
function label(task: Task, prefix?: string): string {
  return `${prefix ?? ""}${task.title}`;
}

function paginate<T>(items: T[], page: number, size = 20): T[] {
  return items.slice(page * size, (page + 1) * size);
}
```

הדוגמה השנייה משתמשת ב-*גנרי*, שנסתכל עליו הבא.

## גנריים, ברוגע

גנרי הוא פרמטר טיפוס — מציין מקום ל"טיפוס כלשהו שנמלא באתר הקריאה". השימוש הקלאסי הוא פונקציה שעובדת על כל מערך בלי לאבד מידע טיפוס:

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

first([1, 2, 3]);            // T הוא number; מחזיר number | undefined
first(["a", "b"]);           // T הוא string; מחזיר string | undefined
```

השם `T` הוא קונבנציה. השתמש באותיות בודדות לפרמטרים מאוד כלליים (`T`, `U`, `K`, `V`), או בשמות תיאוריים כשבהירות עוזרת (`<Item>`, `<Payload>`).

תראה גנריים כל הזמן ב-Angular. `signal<Task[]>([])` יוצר סיגנל שמחזיק מערך של `Task`. `HttpClient.get<Task[]>('/api/tasks')` אומר לקומפיילר איזה צורה לצפות בחזרה מהשרת. בכל מקרה, הגנרי הוא התשובה ל"איזה טיפוס נמצא בתוך הדבר?".

אל תכתוב פונקציות גנריות משלך כשאתה לומד. פנה אליהן בפעם השלישית או הרביעית שאתה מעתיק ומדביק פונקציה ורק משנה את הטיפוסים שלה. עד אז, פונקציות עם טיפוסים רגילים הן כמעט תמיד הכלי הנכון.

## הסקת טיפוסים היא חברה שלך

TypeScript אגרסיבית בהסקת טיפוסים, וכדאי לך לתת לה. שקול:

```ts
const tasks = tasksFromServer();          // מוסק כ-Task[]
const titles = tasks.map(t => t.title);   // מוסק כ-string[]
const activeCount = tasks.filter(t => !t.done).length;  // מוסק כ-number
```

לא היו צריכות הערות — TypeScript צעדה דרך כל השרשרת והבינה. הכלל הכללי: הוסף הערות ל*כניסות* ול*יציאות* של הפונקציות הציבוריות שלך, ותן ל-TypeScript להסיק את כל השאר.

## `any`, `unknown`, ופתחי המילוט הכנים

לפעמים אתה באמת לא יודע את הטיפוס של ערך — פשוט ניתחת קצת JSON מהחוט, או אתה קורא לספרייה ישנה בלי טיפוסים. ל-TypeScript יש שני פתחי מילוט:

- **`any`** מכבה בדיקת טיפוסים לערך הזה. הכל מותר. זה מסוכן; אם אתה כותב `any` אתה חותם ומוותר על כל היתרון של שימוש ב-TypeScript עבור הפיסת מידע הזאת.
- **`unknown`** היא החלופה הבטוחה. ערך של טיפוס `unknown` יכול להיות כל דבר, אבל אתה לא יכול לעשות שום דבר *איתו* עד שתצמצם אותו לטיפוס ספציפי קודם.

```ts
function parseTask(raw: unknown): Task {
  if (typeof raw !== "object" || raw === null) {
    throw new Error("Not an object");
  }
  const r = raw as { id?: unknown; title?: unknown; /* ... */ };
  if (typeof r.id !== "string" || typeof r.title !== "string") {
    throw new Error("Missing required fields");
  }
  // ...בדיקות נוספות...
  return { id: r.id, title: r.title, done: false, createdAt: "", dueDate: null, tags: [] };
}
```

פנה ל-`unknown` בגבול של האפליקציה שלך — ניתוח JSON, קריאת `localStorage`, טיפול בספריות בלי טיפוסים. פנה ל-`any` כמעט אף פעם.

## דקורטורים, בקצרה

Angular מסתמכת בכבדות על *דקורטורים* — פונקציות שנכתבות עם קידומת `@` שמצמידות מטא-דאטה למחלקה או לחברים שלה. תראה אותם כל הזמן:

```ts
@Component({
  selector: "app-task-row",
  template: `<div>{{ task.title }}</div>`,
})
export class TaskRow {
  @Input() task!: Task;
}
```

לעת עתה, דע רק זאת: `@Component`, `@Input`, `@Output`, וחבריהם הם איך שאתה אומר ל-Angular "המחלקה הזאת היא קומפוננטה" או "השדה הזה הוא input מהורה". פרק 5 יסביר מה כל אחד עושה. תפקידה של TypeScript הוא פשוט לאפשר את התחביר; המשמעות היא של Angular.

> **הערה.** דקורטורים סטנדרטים רשמית ב-JavaScript מודרני עכשיו, אבל Angular עדיין משתמשת בטעם ה*ניסיוני* הישן יותר כי הוא נושא יותר מטא-דאטה ש-Angular מסתמכת עליה. ה-CLI של Angular מגדיר את הפרויקט שלך כך שזה פשוט יעבוד; אתה אף פעם לא צריך לחשוב על זה. אם אי פעם תראה `experimentalDecorators` ב-`tsconfig.json`, זו הסיבה.

## האופרטורים `!` ו-`?`

שני סימנים קטנים ייחודיים ל-TypeScript יופיעו לעתים קרובות:

- `x!` הוא *טענת non-null*. הוא אומר לקומפיילר "סמוך עליי, זה לא null או undefined כאן". השתמש בו במידה; כל `!` הוא מקום שבו יכולה להופיע שגיאת זמן ריצה שמערכת הטיפוסים לא מזהירה עליה. בקוד קומפוננטה, `@Input() task!: Task` משתמש ב-`!` כדי להבטיח "Angular תקצה את זה לפני שאשתמש בו", וזאת הבטחה ש-Angular מקיימת — אבל רק אחרי בניית הקומפוננטה, לא במהלכה.
- `x?.y` הוא אופרטור *שרשור אופציונלי* (שהוא בעצם JavaScript רגיל). הוא מחזיר `undefined` בקצר-מסלול אם `x` הוא `null` או `undefined`, במקום לזרוק. `x?.y ?? "default"` משלב אותו עם אופרטור *nullish coalescing* שנפגוש בפרק 3.

## מה דילגנו עליו במכוון

ל-TypeScript יש טיפוסים מותנים, טיפוסים ממופים, טיפוסי template literal, `infer`, איחודים מובחנים במלוא הכלליות שלהם, ומאה כלים אחרים. תיתקל בחלקם, בעיקר בהודעות שגיאה, ותתפתה לצלול לחור הארנב הזה. התנגד. התכונות בפרק הזה הן אלה שתשתמש בהן כל יום ב-Angular. השאר זמין כשתצטרך אותו.

## מה בא הלאה

פרק 3 מכסה את התכונות של JavaScript המודרני ש-Angular מניחה שאתה יודע: מודולים, פונקציות חץ, destructuring, spread ו-rest, `async`/`await`, ושיטות המערך שתישען עליהן ללא הפסקה. אם כבר כתבת JavaScript עדכני, אתה יכול לסקור אותו במהירות; אם לא, קח את זה לאט — פרק 4 יניח כל רעיון מפרק 3.

### תרגילים

1. כתוב interface `Habit` עם השדות האלה: `id` (string), `name` (string), `frequency` (אחד מ-`"daily"`, `"weekly"`, `"custom"`), `color` (string אופציונלי), `createdAt` (string מסוג `readonly`). אז כתוב פונקציה `describe(habit: Habit): string` שמחזירה משהו כמו `"Read (daily)"`.

2. בהינתן `type Result<T> = { ok: true; value: T } | { ok: false; error: string }`, כתוב פונקציה `unwrap<T>(r: Result<T>): T` שמחזירה את הערך אם `ok` הוא true וזורקת אחרת. נסה לכתוב את זה עם צמצום ולא עם טענת `as`.

3. ב-Playground (`typescriptlang.org/play`), הדבק אובייקט בצורה `{ title: "test", priority: "high" }` ונסה להקצות אותו למשתנה בטיפוס `{ title: string; priority: number }`. קרא את הודעת השגיאה בקפידה. אחר כך תקן את האובייקט כך שיעבור בדיקת טיפוסים. הבנת פורמט השגיאה הזה היא מיומנות שכדאי שתהיה.
